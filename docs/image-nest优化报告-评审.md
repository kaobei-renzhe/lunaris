## 〇、结论摘要

这份报告的**骨架是好的**：五段式（功能／体验／性能／稳定性／打包）分类清楚，条目普遍能落到具体文件，性能与稳定性两块抓得准，B1（打包瘦身）是真正立竿见影的发现。

但它**不能按原样"直接交由 Trae 逐条实现"**：有 4 处与源码事实不符、2 处建议与项目既定约束冲突、编号体系与优先级撞车、所有条目缺少验收标准与回滚方案，且完全缺失安全、测试、数据恢复三个维度。

| 维度 | 评分 | 主要依据 |
| --- | --- | --- |
| 内容准确性 | 6.0 / 10 | 4 处硬性事实错误（U5、S8、F8、B1 成因），单位混用，代码规模低估 27% |
| 逻辑一致性 | 6.5 / 10 | `P1/P2/P3` 同时表示条目与优先级；"先做完再上新功能"与第一批塞入新功能自相矛盾；F8≈S8、F3≈U7 重复 |
| 表述清晰度 | 7.5 / 10 | 句式统一、结论前置；但大量"必然/完全没有/显著"等绝对化措辞，量化收益无依据 |
| 结构合理性 | 7.5 / 10 | 分类清晰、可检索；缺"安全""测试与质量""数据恢复"章节，ID 与优先级两套编码混淆 |
| 实操可行性 | 5.5 / 10 | 无验收标准、无验证方法、无风险与回滚、无接口/表结构契约；F1 低估破坏性；P7 与"闲时索引"约束冲突 |
| 完整性 | 6.0 / 10 | 漏安全基线（sandbox:false、无 CSP）、零测试现状、发布流程、许可证与模型供应链、可访问性 |

**建议先修的 8 处**（按性价比排序）

1. 删掉/改写 U5：`在资源管理器中显示` 按钮**已经存在**，这条是重复建设。
2. 重写 S8：`trashItems` 是**有意**保留缩略图以便撤销，真正的缺口是"没有永久删除入口"（`purgeItems` 写了却从未被调用）。
3. 修正 B1 归因：冗余来自 `files` 默认包含全部生产依赖，不是 `asarUnpack` 造成的。
4. 修正 P1 论据：是 **4 次像素解码 + 1 次头部读取**，不是"5 次完整解码"；把"下降 40%–60%"改成待测假设。
5. 拆分 F1：把"批量改库内元数据"（安全）与"批量改磁盘文件名"（高风险）分成两条，后者必须带 dry-run 与撤销。
6. 给 P7 补约束：现有 2 线程是"闲时不抢占 CPU"的设计结果，不能只写"提速数倍"。
7. 统一编号：`P1…P10` 改为 `PERF-01…`，`P0–P3` 只表示优先级。
8. 给所有 P0/P1 条目补四要素：验收标准、验证方法、风险、回滚方案。

### 2.3 数据口径问题

- **单位混用**：B2 用十进制 MB（`onnxruntime.dll` 27.4 MiB = 28.7 MB 写成 28.7 MB），B1 的 `win32/x64 64MB` 却是 MiB（十进制应为 67 MB）。同一份报告里两种口径并存，导致"224 MB"到底是 MiB 还是 MB 无法判断（实测 223.1 MiB）。
- **收益无基线**："导入耗时下降 40%–60%""索引速度数倍提升""亚秒级"均无测量方法、无样本量、无硬件描述。建议统一写成"假设 + 验收阈值"，并补基线脚本（见 G2）。
- **行号会漂移**：报告把行号当锚点（这是优点），但没有标注 commit/版本，本次核对已发现 `ipc.ts` 行号随近期改动变动。建议"符号名为主、行号为辅"，并写明核对时的 commit。

## 五、结构合理性

**做得好的**：分类可检索、每条有文件锚点、有实施顺序章节、有结论摘要。

**需要调整的**：

1. **缺三个必备章节**：安全基线、测试与质量、数据安全与恢复（详见第七节）。对一款"管理用户全部照片索引"的本地工具，这三块的重要性不低于性能。
2. **ID 体系两套并存**：`F/U/P/S/B` 与 `P0–P3` 混用（见 L1）。
3. **同一主题被切散**：灯箱（F3、U7）、缓存（F8、S8）、App 拆分（F9、U6）、配置（B7、P4）分散在不同章节，读者需要自己拼。
4. **难度定义与条目不符**：头部定义"低＝单文件内改动"，但 U2 标"低"却要改 types/preload/ipc/repo/App 五处；F8 标"低—中"却涉及新增配置与设置界面。
5. **缺"总览表"**：没有一张把所有条目压成一行的表（编号、优先级、难度、影响面、依赖、验收），不便排期与验收。

## 六、实操可行性

以下不是"写得不够细"，而是**照做会出错或做不完**的点：

| 编号 | 缺口 | 具体风险 | 建议补充 |
| --- | --- | --- | --- |
| F1 | 批量改名被定为 P0，但几乎没有讨论破坏性 | 改名会牵动 `items.path`、缩略图/预览文件名、dHash 缓存、watcher 抖动、RAW+JPEG 配对、大小写改名、Windows 保留名与长路径、被占用文件、撤销写回；报告只提了"重名冲突与 RAW+JPEG" | 拆两条：① `bulkUpdate` 只改库内元数据（安全，P0）；② 磁盘改名单独一条，必须有 dry-run 预览、冲突策略、逐项撤销、改名失败回滚 |
| F2 | 导出未说明色彩与元数据策略 | 不处理 ICC/方向/EXIF 剥离，导出图会在别的设备上偏色或泄露位置信息 | 明确"不改原图、仅生成副本"，并给出 ICC 保留、按 EXIF 摆正、EXIF/GPS 可选剥离三项开关 |
| F3 | 灯箱缩放只提快捷键 | 没定义缩放层级、拖拽边界、触控板/滚轮行为、与"点击空白退出"的冲突（拖拽结束误触退出） | 补交互规格 + "拖拽中不触发关闭"的验收用例 |
| F4 | 对比视图未定义一致性 | 不同比例、不同焦段的图片如何并排（同高/同宽/同视野）、同步缩放与否 | 给出 2–4 张的布局规则与"同步缩放"开关 |
| F5 | 时间轴未定义时区与缺 EXIF 的兜底 | `mtime` 取 EXIF 拍摄时间，缺 EXIF 时是 0 还是文件时间未说明 | 定义兜底优先级：EXIF → 文件修改时间 → 导入时间，并在 UI 标注"估算" |
| F7 | XMP 侧车未定义边界 | 写到原目录会触发 watcher；与"不改原图"原则的关系未说明 | 明确只写同名 `.xmp`、watcher 忽略、冲突策略（应用库优先/文件优先） |
| F8/S8 | 缓存策略缺"谁在用" | 删缓存可能删掉正在灯箱显示的预览 | 补引用计数或"仅清理 N 天未访问"的安全策略 |
| P3 | 同步 I/O 改异步的影响面被低估 | better-sqlite3 本身是同步的，真正能异步的只有 `fs`；改造期间要注意"异步化后并发写入顺序"变化 | 列出可改/不可改清单，并明确"DB 写入仍走单线程事务" |
| P6 | 缺性能基线与验收 | 没有"多少张、什么硬件、多少 FPS"的基准，改完无法证明 | 补基准脚本 + 验收阈值（如 5 万张、滚动 ≥50fps） |
| B1 | 排除后未要求运行验证 | 原生模块路径被裁错会导致语义搜索直接不可用 | 验收写死：`win-unpacked/bin` 只剩 `win32/x64`，且启动后跑一次文本语义搜索返回结果 |
| 全局 | 无"接口/表结构契约" | 报告说"可直接实现"，但没给 `bulkUpdate` 签名、`items` 新列 DDL、新配置结构 | 每条附最小契约（TypeScript 签名 / SQL / JSON 结构） |

## 七、覆盖遗漏（报告完全没提，但对这个项目重要）

| 编号 | 遗漏项 | 现状证据 | 为什么重要 |
