# 大模型接入模块设计 · MoonNest

> 版本：0.1.17 规划稿（对应代码：`src/main/llm/**`、`src/shared/llm.ts`、`src/renderer/src/components/SettingsDialog.tsx`）
> 面向：后续要接新厂商、新增 AI 能力的开发者。

---

## 1. 定位与边界

| 项 | 说明 |
| --- | --- |
| 做什么 | 统一封装大模型调用：配置、密钥、厂商差异、超时重试、错误归一、调用统计、能力插件 |
| 不做 | 不在渲染层发请求；不保存明文密钥；不做流式（当前为一次性返回） |
| 安全边界 | 密钥只在主进程内存中出现，落盘前用系统加密（Windows DPAPI / macOS Keychain）；渲染层只能看到 `hasKey` 与掩码 `keyHint` |
| 成本边界 | 图片统一压到长边 1024 / JPEG q82；每个能力声明 `maxItems`，超限直接拒绝 |
| 使用入口 | 设置 → 大模型（开关 / 服务商 / 地址 / 模型 / 超时 / 温度 / tokens / 重试 / API Key / 测试连接 / 能力清单） |

## 2. 分层架构

```
渲染层 (React)
  SettingsDialog.tsx  ──window.api.llm*──┐
                                         │  IPC (contextBridge, sandbox: true)
主进程                                    ▼
  src/main/ipc.ts            6 个 llm:* handler
  src/main/llm/index.ts      门面：配置校验 + 能力调度 + 统计 + 错误归一
    ├─ registry.ts           能力注册表（可插拔核心）
    ├─ capabilities/         quality.ts / advice.ts / smartFilter.ts
    ├─ client.ts             超时 / 重试 / 退避 / 取消
    ├─ providers.ts          厂商差异：URL、鉴权头、消息体、响应解析、状态码映射
    ├─ image.ts              sharp 压图 → base64（RAW 回退预览图）
    ├─ keyring.ts            safeStorage 加密读写密钥
    ├─ config.ts             默认值 + clamp + 持久化
    ├─ metrics.ts            调用记录（内存 50 条 + 落日志）
    └─ util.ts               extractJson / normalizeScore
  src/shared/llm.ts          两侧共享的纯类型（无密钥、无逻辑）
```

分层原则：

1. **能力只拿两个原语**：`ctx.chat()` 与 `ctx.image()`。能力代码里没有密钥、没有 HTTP、没有重试逻辑。
2. **厂商差异只出现在 `providers.ts`**：换厂商不影响能力，加厂商不改客户端。
3. **重试与超时只出现在 `client.ts`**：唯一出口，避免重复实现。
4. **配置与密钥分家**：配置进 `settings.json` 的 `llm` 字段，密钥单独走 `llm-key.bin`。

## 3. 配置管理

### 3.1 字段与默认值

| 字段 | 类型 | 默认 | 取值范围 | 说明 |
| --- | --- | --- | --- | --- |
| `provider` | `'openai-compatible' \| 'anthropic'` | `openai-compatible` | 固定枚举 | 非法值回落到兼容 |
| `baseUrl` | string | `https://api.openai.com/v1` | — | 接口根地址，不带具体路径 |
| `model` | string | `''` | — | 空值视为未配置 |
| `temperature` | number | `0.3` | 0 – 2 | 评分类能力会在调用时临时降到 0.2 |
| `maxTokens` | number | `1200` | 16 – 32000 | 单次输出上限 |
| `timeoutMs` | number | `60000` | 5000 – 300000 | 单次请求超时 |
| `maxRetries` | number | `2` | 0 – 5 | 不含首次尝试 |
| `enabled` | boolean | `false` | — | 总开关，关闭时任何能力调用直接拒绝、零网络请求 |
| `capabilities` | `Record<LlmCapabilityId, boolean>` | 三个全开 | — | 每个能力独立开关；关掉后入口隐藏、调用被拒绝 |

### 3.2 读写约定

- 读：`getLlmConfig()` 每次从 `settings.json` 读并做 `clamp`，因此手改配置文件也不会产生越界值。
- 写：`saveLlmConfig(patch)` 是**局部补丁**，只覆盖传入字段。
- 换厂商且 `baseUrl` 仍是旧厂商的默认值时会自动跟随到新默认值；用户自己填过的地址不会被覆盖。

## 4. 密钥管理

| 环节 | 实现 |
| --- | --- |
| 可用性检测 | `safeStorage.isAsyncEncryptionAvailable()`，不可用时 `encryption: 'unavailable'` |
| 保存 | `encryptStringAsync()` 后写 `userData/llm-key.bin`；**加密不可用直接抛错，绝不退化为明文** |
| 读取 | `decryptStringAsync()` 返回 `{ result, shouldReEncrypt }`；`shouldReEncrypt` 为真时顺手重加密 |
| 解密失败 | 换机器/换系统账户导致解不开时按"没有密钥"处理，不崩溃 |
| 清除 | 删除密钥文件；删不掉也无害，读不到即视为无密钥 |
| 展示 | `keyHint()` 形如 `sk-…efgh`，仅用于确认"存的是哪把钥匙" |

> Electron 45 起 `safeStorage` 同步 API 已废弃，全部使用 async 版本。

## 5. 请求链路

### 5.1 厂商适配

| 项 | OpenAI 兼容 | Anthropic |
| --- | --- | --- |
| 端点 | `{baseUrl}/chat/completions` | `{baseUrl}/messages` |
| 鉴权 | `authorization: Bearer <key>` | `x-api-key: <key>` + `anthropic-version: 2023-06-01` |
| 系统提示 | `messages` 内 `role: 'system'` | 抽出为顶层 `system` 字段 |
| 图片 | `image_url: { url: data:<mime>;base64,<data> }` | `image: { source: { type: 'base64', media_type, data } }` |
| JSON 模式 | `response_format: { type: 'json_object' }`（仅要求 JSON 时才带） | 不支持该字段，靠提示词约束 |
| 回复解析 | `choices[0].message.content` | `content[]` 中 `type === 'text'` 拼接 |
| usage 字段 | `prompt_tokens / completion_tokens / total_tokens` | `input_tokens / output_tokens`（合计自行相加） |

`joinUrl()` 允许用户直接填完整端点（如 `https://x/v1/chat/completions`），不会重复拼接。

### 5.2 超时与重试

```
for attempt in 0..maxRetries:
  AbortController + timeoutMs 定时中止
  ├─ 成功 → 返回 { reply, attempts, latencyMs }
  └─ 失败 → 归一为 LlmError
      可重试（network / rate_limit / 5xx / timeout）且未到上限：
        sleep(Retry-After ?? min(8000, 600 * 2^attempt) + random(0~200ms))
      否则抛出
```

- **只有** 网络错误、429、5xx、超时会重试；401/403（鉴权）、400/404/422（请求错误）、响应非法 JSON 一律不重试。
- 退避上限 8 秒，`Retry-After` 优先。
- 外部 `AbortSignal` 取消时立即抛 `cancelled`，不再重试。

### 5.3 错误码表

| 错误码 | 触发 | 可重试 | 用户侧提示方向 |
| --- | --- | --- | --- |
| `not_configured` | 未启用 / 无模型名 / 无 Key | 否 | 去设置补配置 |
| `auth` | 401 / 403 | 否 | 检查 Key 与权限 |
| `rate_limit` | 429 | 是 | 等退避，或降并发 |
| `timeout` | 本地超时 | 是 | 加大超时或换模型 |
| `network` | DNS/连接失败、5xx | 是 | 检查网络/代理 |
| `bad_request` | 400 / 404 / 422、参数非法 | 否 | 模型名/参数/图片有问题 |
| `bad_response` | 响应不是合法 JSON / 结构不符 | 否 | 模型不支持视觉或输出格式跑偏 |
| `cancelled` | 调用方主动取消 | 否 | — |
| `unknown` | 其它 | 否 | 看日志 |

## 6. 能力插件机制

### 6.1 接口

```ts
export interface CapabilityChatOptions {
  json?: boolean
  maxTokens?: number
  temperature?: number
}

export interface CapabilityContext {
  /** 发一轮对话，返回纯文本；JSON 能力自己用 extractJson 解析 */
  chat: (messages: LlmMessage[], options?: CapabilityChatOptions) => Promise<string>
  /** 取一张已压到合适尺寸的图片，作为多模态输入 */
  image: (itemId: number) => Promise<LlmContentPart>
}

export interface LlmCapability<TInput = unknown, TOutput = unknown> {
  id: LlmCapabilityId
  title: string
  description: string
  /** 单次调用允许的最大图片数，用于成本保护；不填表示不限制 */
  maxItems?: number
  run: (ctx: CapabilityContext, input: TInput) => Promise<TOutput>
}
```

`CapabilityContext.chat()` 内部已经完成重试、超时与统计记录——能力实现拿到的是"已经成功的一轮文本"。

### 6.2 新增一个能力（三步）

1. 在 `src/shared/llm.ts` 的 `LLM_CAPABILITY_IDS` 里加 id，并补充入参/出参类型；
2. 新建 `src/main/llm/capabilities/<name>.ts`，实现 `LlmCapability`；
3. 在 `src/main/llm/index.ts` 顶部 `registerCapability(...)` 注册一行。

注册后设置页的能力徽章自动出现，`llm:run` 立即可用，无需改 IPC 与 UI。

### 6.3 内置能力

#### `photo.quality` · 照片质量评分（≤12 张）

| 项 | 内容 |
| --- | --- |
| 入参 | `{ itemIds: number[] }` |
| 出参 | `{ results: PhotoQualityScore[]; failed: Array<{ itemId, message }> }` |
| 评分维度 | `composition` 构图 / `exposure` 曝光 / `color` 色彩 / `sharpness` 清晰度 / `overall` 可用性总分，均 0–100 |
| 调用参数 | `temperature 0.2`、`maxTokens 400`、JSON 模式 |
| 容错 | 逐张 try/catch，单张失败进 `failed`，不影响其它张 |
| 落库 | 走专用通道 `llm:quality`：成功的结果写入 `quality_scores`，返回 `persisted` 条数 |

#### `photo.advice` · 后期优化建议（单张）

| 项 | 内容 |
| --- | --- |
| 入参 | `{ itemId: number }` |
| 出参 | `{ itemId, summary, directions[], parameters[{name,value,why}], styleRefs[] }` |
| 调用参数 | `temperature 0.4`、`maxTokens 800`、JSON 模式 |
| 容错 | 数组字段逐项 `String()` + 长度截断，模型把数组写成字符串也不会抛错 |

#### `photo.smartFilter` · 智能筛选（≤30 张，每批 6 张）

| 项 | 内容 |
| --- | --- |
| 入参 | `{ rule: string; itemIds: number[] }` |
| 出参 | `{ matchedIds: number[]; reasons[{itemId,reason}]; evaluated: number; errors?: string[] }` |
| 分批判 | 每批 6 张，用 `A–F` 标签映射回 `itemId`，避免模型编造 id |
| 容错 | 单批失败写入 `errors`，其余批照常返回 |
| 提示策略 | 判断保守：不确定判为不符合 |
| 交互 | 改动规则立即作废上一次结果（「只看这些」禁用），避免"新规则 + 旧命中"被误应用 |
| 落点 | 工具栏「AI 筛选」→ `SmartFilterDialog`；命中的 id 写进 `FilterState.onlyIds`，工具栏显示规则 chip |

### 6.4 图片准备

```
getItemFile(itemId)
  → sharp().rotate().resize({ width: 1024, height: 1024, fit: 'inside', withoutEnlargement: true })
  → .jpeg({ quality: 82 }) → base64
  解码失败 → 回退 previewPathFor(itemId)（RAW / HEIF / TIFF 用导入时生成的预览）
  两者都不可用 → LlmError('bad_request')
```

单张视觉输入约 100–200 KB（base64 后），是成本与识别准确率折中的结果。

### 6.5 评分结果存储

评分不和原图数据混在一起，单独一张表（与 `embeddings` / `auto_tags` 一致的做法，新增能力不用 ALTER 主表）：

```sql
CREATE TABLE quality_scores (
  item_id     INTEGER PRIMARY KEY,   -- 一张图只留最新一份
  composition INTEGER NOT NULL DEFAULT 0,
  exposure    INTEGER NOT NULL DEFAULT 0,
  color       INTEGER NOT NULL DEFAULT 0,
  sharpness   INTEGER NOT NULL DEFAULT 0,
  overall     INTEGER NOT NULL DEFAULT 0,
  comment     TEXT    NOT NULL DEFAULT '',
  model       TEXT    NOT NULL DEFAULT '',  -- 记录产生分数的模型，便于换模型后识别过期结果
  updated_at  INTEGER NOT NULL
);
CREATE INDEX idx_quality_overall ON quality_scores(overall DESC);
```

读写约定：

| 场景 | 实现 |
| --- | --- |
| 写入 | `repo.saveQualityScores()`，事务批量 upsert，同一张图覆盖旧分数 |
| 读取 | `mapItems()` 批量带出，挂到 `Item.quality`，列表/详情/卡片角标共用一份数据 |
| 排序 | `FilterState.sort = 'ai'`，用 `coalesce(子查询, -1) DESC`，没评分的排在最后（AI 关闭时该选项隐藏并复位，见 7.4） |
| 筛选 | `minAiScore`（≥60/70/80/90）与 `unscored`（只看没评分的）；AI 关闭时整个下拉隐藏并复位，见 7.4 |
| 清理 | `purgeItems()` 一并删除对应评分；软删除保留，Ctrl+Z 后分数还在 |
| 失效 | 换文件（`file_mtime` 变化）或换模型都不会自动清分，属于已知取舍，见第 11 节 |

## 7. 对外接口

### 7.1 渲染层（`window.api`）

| 方法 | 签名 | 说明 |
| --- | --- | --- |
| `llmStatus` | `() => Promise<LlmStatus>` | 配置 + 是否已存 Key + 掩码 + 加密可用性 + 最近调用 + 能力清单 |
| `llmSaveConfig` | `(patch: Partial<LlmConfig>) => Promise<LlmStatus>` | 局部更新配置，返回最新状态 |
| `llmSaveKey` | `(key: string) => Promise<LlmStatus>` | 加密保存密钥；加密不可用时抛错 |
| `llmClearKey` | `() => Promise<LlmStatus>` | 删除密钥 |
| `llmTest` | `() => Promise<LlmTestResult>` | 发一条 8 token 的极短请求验证链路（不抛错，返回 `ok/message/latencyMs`） |
| `llmRun` | `(capabilityId: string, input: unknown) => Promise<LlmRunOutcome>` | 执行能力；成功 `{ ok: true, data }`，失败 `{ ok: false, code, message }` |
| `llmScore` | `(itemIds: number[]) => Promise<LlmRunOutcome<PhotoQualitySaved>>` | 评分并落库；`data` 含 `results / failed / persisted` |

> 为什么用信封而不是抛异常：IPC 抛出的 `Error` 到了渲染层只剩 message，`code` 会丢，界面就没法区分"没配置"和"被限流"。所以主进程在 `llm:run` 里 catch 后把错误码一起返回。

对应 IPC 通道：`llm:status`、`llm:config:save`、`llm:key:save`、`llm:key:clear`、`llm:test`、`llm:run`、`llm:quality`。

### 7.2 主进程内部

```ts
import { getStatus, runCapability, testConnection } from './llm'

const status = await getStatus()
const result = await runCapability('photo.quality', { itemIds: [12, 13] })
```

### 7.3 界面入口

| 位置 | 能力 | 状态 |
| --- | --- | --- |
| 设置 → 大模型 | 配置 / 密钥 / 测试连接 / 能力清单 | 已接 |
| 详情面板（右侧单张）→「AI 评分」 | `photo.quality` | 已接，分数落库并显示四维条形 |
| 详情面板（右侧单张）→「AI 后期建议」 | `photo.advice` | 已接（`AdviceDialog`） |
| 工具栏选中条 →「AI 评分」 | `photo.quality` | 已接，一次最多 12 张 |
| 工具栏筛选行 →「AI 评分」下拉 + 排序「AI 评分」 | 落库数据 | 已接 |
| 工具栏筛选行 →「AI 筛选」 | `photo.smartFilter` | 已接（`SmartFilterDialog`），结果变成可取消的规则 chip |

**AI 是可选项，默认不花钱：**

- `aiReady = enabled && hasKey && model`，三项缺一不可；未就绪时相册里**完全不出现** AI 入口（评分 / 建议 / 筛选，以及排序与筛选里的 AI 选项全部隐藏），想看这些功能就去设置打开，避免灰按钮造成误导与误点。
- 设置里另有**三个独立开关**（照片质量评分 / 后期优化建议 / 智能筛选），默认全开。总开关打开后，关上某一个：对应入口直接从相册里消失，主进程也会拒绝调用（`not_configured`，提示"「后期优化建议」已在设置里关闭"）。
- 后期建议弹窗打开后**不会自动请求**，必须手动点「生成建议」；筛选弹窗同理，必须先点「开始筛选」。
- 所有弹窗底部都写明"点按钮才会发请求、会消耗 token"。
- 「测试连接」也是手动触发（8 token 的极短请求）。
- 评分入口跟着收紧：总开关关闭或「照片质量评分」被关时，排序里的「AI 评分」和筛选里的「AI 评分 ≥ / 未评分」一并隐藏，并自动复位已选中的 AI 条件——细节见 7.4。卡片角标与详情里的已有分数不受影响（只读本地数据、零成本）。

`AdviceDialog` 的交互约定：

- **打开不调用**：初始为 idle，显示"点「生成建议」才会发请求"，用户点按钮才开始；
- 三态：生成中 / 成功 / 失败；
- 失败按错误码给下一步提示（未配置或鉴权失败时直接给「去设置」按钮）；
- 快捷键 Esc 关闭、点击遮罩关闭；
- 成功后给「复制」与「重新生成」，底部常驻"建议由大模型生成，仅供参考"。

### 7.4 入口显隐与自动复位

#### 两个判定

| 变量 | 取值 | 用途 |
| --- | --- | --- |
| `aiReady` | `enabled && hasKey && model.trim()` | 区分"还没配好"与"不想用某个能力" |
| `canX` | `config.capabilities[id] !== false` | 单个能力的开关（评分 / 建议 / 筛选） |

#### 显隐矩阵

| 状态 | 相册里的 AI 按钮 |
| --- | --- |
| 主开关未就绪 | **全部不渲染**（评分 / 建议 / 筛选、排序与筛选里的 AI 选项），需要时去「设置 → 大模型」开启 |
| 主开关就绪 + 该能力开 | 正常显示 |
| 主开关就绪 + 该能力关 | 该按钮**不渲染**（评分 / 建议 / 筛选互不影响） |

评分的数据入口（排序「AI 评分」、筛选「≥60… / 未评分」）额外一条规矩：只有 `aiReady && canScore` 为真才渲染。

#### 自动复位（避免"隐形过滤"）

隐藏入口后，如果查询条件还留着，用户会看到"图莫名变少 / 排序莫名其妙"却找不到任何可见的条件。所以隐藏的同时做一次复位：

| 项 | 行为 |
| --- | --- |
| 触发条件 | `aiScoreAvailable = aiReady && capabilities['photo.quality'] !== false` 为假 |
| `filter.sort === 'ai'` | 复位为 `'added'`（最新导入） |
| `filter.minAiScore` | 复位为 `0`（全部 AI 评分） |
| `filter.unscored` | 复位为 `false` |
| `filter.onlyIds`（AI 筛结果） | **不复位**：对应 chip 仍在工具栏显示、可点 × 取消，避免用户没法退出该视图 |
| 已落库的分数 / 卡片角标 / 详情四维分 | **保留并照常显示**（只读本地数据，零成本） |

实现：`App.tsx` 里的一个 `useEffect`，依赖 `[aiScoreAvailable, filter.sort, filter.minAiScore, filter.unscored]`；条件不成立时直接 `return`，不产生多余 `setState`，因此不会触发循环刷新。

已知边界：

- 从智能文件夹载入的筛选若带 AI 条件，载入后同样会被复位（因为对应能力或总开关此刻不可用）。
- 重新打开 AI 能力**不会**自动恢复之前被复位掉的排序 / 筛选，需要手动再选一次——这是有意的取舍：宁可少一点记忆，也要保证"界面所见 = 查询所用"。

## 8. 使用示例

### 8.1 批量评分（渲染层）

```ts
const ids = selectedIds.slice(0, 12)
const outcome = await window.api.llmScore(ids) // 评分 + 落库一次搞定
if (!outcome.ok) {
```

## 9. 可观测性

- **调用记录**：每次调用写一条 `LlmCallSummary`（时间、能力 id、是否成功、尝试次数、耗时、错误码、token 用量），内存保留最近 50 条，设置页展示最近一条与列表。

- **测试连接**：专门的 `llm.test` 记录类型，便于区分"链路探测"与"业务调用"。

## 10. 成本与风险控制

| 风险 | 已有措施 | 后续可加 |
| --- | --- | --- |
| 误点按钮就花钱 | 总开关默认关；未启用时入口只引导去设置、零请求；建议/筛选弹窗都不自动调用；三个能力可单独关闭 | 每次调用前二次确认（可选） |

| 模型胡编 JSON | `extractJson` 括号配平 + 字段级兜底 + 评分归一 1–10 → ×10 | 结构校验库 |
| 关掉功能仍发请求 | `enabled` 为假时 `readyState()` 直接拒绝 | — |

## 11. 已知限制与扩展路线

当前限制：

- 一次性返回，**无流式**（长文本建议场景体验一般）。
- 无跨能力并发控制与队列，批量只能靠各能力内部分批。
- 无结果缓存，同一张图重复生成建议会重复计费（建议弹窗每次打开都会重新调用）。
- 评分已落库，但**没有失效机制**：原图被替换（`file_mtime` 变化）或换了模型，旧分数不会自动清空，需要手动重评。
- 智能筛选**只筛当前已加载的前 30 张**（能力上限），不是全库；命中的 id 存在 `FilterState.onlyIds` 里，刷新或换筛选条件后不保留。
- AI 筛选结果与其它条件叠加时，只在这 30 张里继续叠加。

建议的下一步（按收益排序）：

1. 评分配置"只评未评分的"一键补全（配合已有的 `unscored` 筛选，做成串行队列 + 进度条）；
2. 建议结果落库或缓存（`itemId + mtime + 能力 id` 作键），避免反复点"重新生成"重复付费；
3. 智能筛选接入筛选面板的"自然语言规则"输入框，结果转成 `ids` 过滤；
4. 流式输出与进度回调（`llm:run` 增加事件通道），批量评分时能显示进度；
5. 多模型路由：按能力指定 `model`（评分用小模型、建议用大模型）。
