# 人像工作台 · 实施方案

> 目标：给「月相」加一个独立的人像分类体系视图。
> 形态：**独立工作台页面**（左维度 / 中瀑布流 / 右详情），而不是塞进现有侧栏。
> 状态：**P1 已落地**（facets / tags.facet_id / 工作台 / 维度筛选 / 自定义维度）；P2–P4 待排期，见文末「落地记录」。

---

## 0. 为什么是独立视图

| 理由 | 说明 |
| --- | --- |
| 维度太多 | 9+ 个人像维度塞进现有 Sidebar（236px）会把导航挤爆 |
| 布局冲突 | 需要三栏（筛选 / 网格 / 详情），与主图库的两栏结构不兼容 |
| 会长东西 | 后续的作品集、客户选片、场地档案、模特档案都往这里长，塞侧栏没有生长空间 |

代价：多一个视图状态要维护。收益：这块以后能独立成"业务模块"，不拖累主图库。

## 1. 核心设计：三层分类

一张照片的描述分三种东西，**不能混成一套扁平标签**：

```
场次 Shoot ── 一次拍摄，填一次，整组继承（日期/客户/场地/天气/场景）
   │
   ├── 画面属性 Facet Tags ── 每张各不相同（景别/色调/氛围/情绪/光线）
   │
   └── 实体档案 Entities ── 跨组复用，有独立档案（模特/服装/场地/道具/妆发）
```

- **画面属性** → 复用 `tags` 表，加 `facet_id` 列。NULL 就是老标签，**零迁移**。
- **实体** → 独立 `entities` 表，`kind` 区分类型，`meta` 存 JSON。
- **场次** → 独立 `shoots` 表，`items.shoot_id` 外键。
- **器材** → 不新建，复用现有 `gear.json` 装备库 + EXIF 自动识别。

## 2. 数据模型

### 2.1 新增表

```sql
-- 维度定义：完全自定义，加维度不用改代码
CREATE TABLE IF NOT EXISTS facets (
  id          TEXT PRIMARY KEY,        -- 'shot_size' / 'mood' / 用户自定义
  name        TEXT NOT NULL,           -- '景别'
  multi       INTEGER NOT NULL DEFAULT 1,  -- 同维度是否可多选
  auto_source TEXT,                    -- 'local' | 'clip' | 'llm' | NULL
  sort        INTEGER NOT NULL DEFAULT 0,
  builtin     INTEGER NOT NULL DEFAULT 0
);

-- 场次
CREATE TABLE IF NOT EXISTS shoots (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  title    TEXT NOT NULL DEFAULT '',
  shot_at  INTEGER,
  client   TEXT,
  venue_id INTEGER,                    -- → entities.id (kind='venue')
  note     TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL
);

-- 实体档案
CREATE TABLE IF NOT EXISTS entities (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  kind       TEXT NOT NULL,            -- model | wardrobe | venue | prop | hmu
  name       TEXT NOT NULL,
  meta       TEXT NOT NULL DEFAULT '{}',  -- JSON，按 kind 决定字段
  cover      TEXT,                     -- 封面缩略图相对路径
  created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_entities_kind ON entities(kind);

CREATE TABLE IF NOT EXISTS item_entities (
  item_id   INTEGER NOT NULL,
  entity_id INTEGER NOT NULL,
  role      TEXT,                      -- 可选：这张里它是主角/背景/借位
  PRIMARY KEY (item_id, entity_id)
);
CREATE INDEX IF NOT EXISTS idx_item_entities_ent ON item_entities(entity_id);
```

### 2.2 给现有表加列

```sql
ALTER TABLE tags   ADD COLUMN facet_id TEXT;   -- NULL = 普通标签
ALTER TABLE items  ADD COLUMN shoot_id INTEGER;
```

**迁移写法**：`db.ts` 现有模式是 `CREATE TABLE IF NOT EXISTS` 一把梭，但加列必须判断存在。建议在 `db.ts` 加辅助函数：

```ts
function ensureColumn(database: Database.Database, table: string, column: string, ddl: string): void {
  const cols = database.prepare(`PRAGMA table_info(${table})`).all() as { name: string }[]
  if (!cols.some((c) => c.name === column)) database.exec(`ALTER TABLE ${table} ADD COLUMN ${ddl}`)
}
// 调用
ensureColumn(db, 'tags', 'facet_id', 'facet_id TEXT')
ensureColumn(db, 'items', 'shoot_id', 'shoot_id INTEGER')
```

`getEntityDetail` 里的 `coEntities` 是"这个模特合作过哪些场地/化妆师"，靠一次自连接拿：

```sql
SELECT e.*, COUNT(*) AS n FROM item_entities a
JOIN item_entities b ON b.item_id = a.item_id AND b.entity_id != a.entity_id
JOIN entities e ON e.id = b.entity_id
WHERE a.entity_id = ? GROUP BY e.id ORDER BY n DESC LIMIT 12
```

### 3.3 新文件 `src/main/shoots.ts`

```ts
export function listShoots(): ShootWithCount[]
```

## 4. 筛选语义（关键）

**同一维度内 OR，维度之间 AND。**

```ts
// FilterState 增加一个字段，不动现有 tagIds
export interface FilterState {
  // ...
  /** 人像维度：facetId → 选中的 tagId 列表（同维度 OR，跨维度 AND） */
  facets?: Record<string, number[]>
}
```

SQL 生成（`repo.ts` 里拼 WHERE）：

```sql
-- 每个 facet 生成一个 IN，整体 AND
AND EXISTS (SELECT 1 FROM item_tags it WHERE it.item_id = items.id AND it.tag_id IN (?,?))
AND EXISTS (SELECT 1 FROM item_tags it WHERE it.item_id = items.id AND it.tag_id IN (?))
```

⚠️ **动工前必读**：现在 `tagIds` 是「同时有这些标签」，语义和新 `facets` 不同，两个字段要分别走各自的分支，**不要合并**，否则老用户存的智能文件夹会全部变味。

## 6. AI 预填分层

| 维度 | 引擎 | 成本 | 精度预期 |
| --- | --- | --- | --- |
| 色调 | 本地：直方图 + 白平衡 | 0 | 高 |
| 高调/低调 | 本地：亮度分布 | 0 | 高 |
| 景别 | 本地：人脸框面积占比 | 0 | 中高 |
| 时段 | EXIF DateTimeOriginal | 0 | 确定 |
| 场景 | CLIP 零样本（现成模型） | 0 | 中 |
| 氛围 | CLIP 零样本 | 0 | 中 |
| 天气 | CLIP + EXIF 时间 | 0 | 中低（仅室外有效） |
| 情绪 | 大模型看图 | 💰 | 中，主观 |

**预填结果一律标记 `pending`**，界面上用琥珀小点提示，用户点「全部确认」才转正。没有确认的不会被当作准确数据参与检索排序。

情绪是唯一花钱项，默认**不自动跑**，用户在详情面板手动点「AI 猜情绪」才发请求（沿用现有 LLM 开关与成本控制）。

## 7. 分期与验收

| 期 | 内容 | 验收标准 |
| --- | --- | --- |
| **P1** | facets 表 + tags.facet_id + 工作台骨架 + 维度筛选 + 自定义维度 | 能按「晴天 × 特写 × 暖调」筛出结果；能新建一个叫「道具」的维度并打标；老的智能文件夹行为不变 |
| **P2** | 场次表 + 自动归组 + 批量继承 + 实体档案 + 实体详情页 | 导入 200 张能自动建议成 3 个场次；点模特能看他所有片子；批量给一组打景别 |
| **P3** | 本地预填（色调/景别/时段/场景/氛围）+ 待确认交互 | 导入后 80% 的照片已有色调节别建议，用户只需扫一眼 |
| **P4** | 情绪走 LLM + 作品集生成 | 按筛选条件一键导出可发给客户的一页图册 |

**建议先只做 P1**：不碰 AI、不花钱、纯数据结构和界面，一周内能验收。等真用两周，自然知道哪些维度是废的，再决定 P2 怎么落。

## 8. 风险与回滚

| 风险 | 应对 |
| --- | --- |
| 维度设计跑偏，做了一堆没人用的 | `facets` 全动态，删维度只需一条 UPDATE，不触发数据迁移 |
| 老标签体系被污染 | `facet_id` 为 NULL 即老标签，筛选走各自分支，互不干扰 |
| 打标成本还是太高 | P3 的预填是核心，若 P3 效果差，就退化到"只按场次填" |
| 实体档案字段设计不合理 | `meta` 存 JSON，改字段不动表结构，前端做 schema 校验 |
| 工作台与主图库状态不同步 | 工作台只读同一份 `items`，共享 `currentId`，不做第二套缓存 |

回滚：P1 只加表、加列、加新视图，**不改任何现有查询**。真出问题删掉新文件 + 移除入口即可，老功能零影响。
