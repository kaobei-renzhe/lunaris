# 月巢（image-nest）实施计划

> 依据：[《image-nest 优化报告》评审与优化建议](./image-nest优化报告-评审.md)
> 代码基线：`package.json` 0.1.14，Electron 45 / React 19 / better-sqlite3 13 / sharp 0.35
> 规模标注：S = 单点改动（1–2 文件）；M = 跨 3–5 文件或新增 IPC；L = 涉及数据模型/架构
> 本计划不含工期估算，只给顺序、依赖、验收与回滚。

---

## 一、目标与原则

**总目标**：先把"可观测 + 可回归"立起来，再用低风险改动换用户可感知的提升，最后才做会动数据模型的功能。

四条硬约束（全程不得违反）：

1. **不改用户原图内容**。改名、导出、XMP 都属于"显式确认的例外"，各自必须有撤销或 dry-run。
2. **不抢占前台资源**。语义索引维持"闲时 + 2 线程 + 可中断"，任何提速方案不得突破这个上限。
3. **不破坏既有数据**。任何 schema 变更前自动备份 `library.db`，失败可回滚。
4. **每项改动必须可验证**。没有验收标准的条目不进入开发。

**完成定义（DoD）**：`npm run typecheck` + `npm run build` 通过；验收用例通过；有回滚方式；日志覆盖新增的失败分支。

## 二、范围

### 本期做

观测底座、性能、打包瘦身、灯箱与右键菜单、批量元数据、导出、缓存生命周期、schema 版本化。

### 本期不做（写死，避免范围膨胀）

- 视频支持（原 F10）：Electron 自带 `ffmpeg.dll` 是 Chromium 的解码库，不是 CLI，抽帧要另外引依赖。
- 跨平台打包（原 B5）。
- 云同步、账号体系。
- 显影/调色（产品定位是"管理与检索"）。

## 三、阶段与任务卡

### 阶段 0：观测与安全底座（不做完不进入阶段 1）

#### T0-1 结构化日志（S→M）

- **目标**：任何失败都能在日志里定位到模块、路径、堆栈。
- **改动**：
  - 新增 `src/main/logger.ts`：`userData/logs/moonnest-YYYY-MM-DD.log`，级别 `info/warn/error`，单文件 5 MB 轮转、保留 5 份。
  - 接入点：`importer.ts`（catch、跳过重复、HEIF 兜底失败）、`watcher.ts`（监听失败目录）、`embeddings.ts`（失败计数汇总）、`relocate.ts`、`db.ts`（迁移/打开失败）。
  - 路径脱敏：把 `C:\Users\<name>\` 替换为 `%USERPROFILE%`。
- **契约**：`log.info(scope: string, message: string, meta?: Record<string, unknown>)`
- **验收**：
  1. 导入一个损坏文件 → 日志出现 `scope=import`、含文件路径与错误消息。
  2. 单文件超过 5 MB 自动切分，旧文件按数量淘汰。
  3. 日志中不出现完整用户名路径。
- **风险/回滚**：写日志本身失败不得影响主流程（try/catch 吞掉）；回滚＝移除调用点。

#### T0-2 崩溃兜底（S）

- **目标**：崩溃可感知、可记录，退出前不丢 WAL。
- **改动**：`src/main/index.ts` 注册 `process.on('uncaughtException' | 'unhandledRejection')`、`app.on('render-process-gone' | 'child-process-gone')`；退出路径调用 `closeLibrary()` 前显式 `wal_checkpoint(TRUNCATE)`（在 `db.ts` 的 `closeLibrary` 内实现）。
- **验收**：手动 `throw` 一次 → 进程不静默退出、日志有记录；异常退出后重启，`library.db-wal` 尺寸回落。
- **风险**：`uncaughtException` 后进程状态不可信 → 记录后仍退出，不做"继续运行"。

#### T0-3 基准与冒烟脚本（M）

- **目标**：让后续所有"提升 X%"有据可查。
- **新增**：`scripts/bench-import.mjs`（用 sharp 生成 200 张混合尺寸 JPG/PNG 到临时目录，跑 `importPaths`，输出耗时/内存/失败数）、`scripts/bench-query.mjs`（对现有库测 `listItems` 首页、`filteredIds`、语义搜索耗时）。
- **产物**：`.cache/bench/<timestamp>.json`，含机器信息、版本号。
- **验收**：两次运行同参数偏差 < 15%；`npm run bench` 可独立执行。
- **备注**：这是阶段 1 所有收益结论的唯一依据。

#### T0-4 安全基线（M）

- **目标**：补上评审指出的 `sandbox:false` 与无 CSP。
- **改动**：
  - `src/renderer/index.html` 增加 CSP meta：`default-src 'self'; img-src 'self' data: blob: thumb: photo:; style-src 'self' 'unsafe-inline'; script-src 'self'`。
  - 评估 `webPreferences.sandbox: true`：当前 preload 只用 `ipcRenderer` / `contextBridge` / `webUtils`，需先确认沙箱下 `webUtils.getPathForFile` 是否可用；不可用则保持 `sandbox:false` 并在计划中记录原因。
- **验收**：控制台无 CSP 违规；缩略图、灯箱、拖拽导入、剪贴板全部正常。
- **风险**：CSP 可能拦截内联样式 → 保留 `style-src 'unsafe-inline'`（Tailwind 运行时写 style）。

### 阶段 1：低风险高收益（P0 主体）

#### T1-1 批量 IPC（M）——替代原 U2

- **改动**：
  - `src/main/repo.ts`：`bulkUpdate(ids, patch)`，用现有 `chunk(list, 400)` 分组，`db.transaction` 包住；按 patch 字段动态生成 `UPDATE items SET ... WHERE id IN (...)`。
  - `src/main/ipc.ts` / `src/preload/index.ts` / `src/shared/types.ts`：新增 `items:bulkUpdate`。
  - `src/renderer/src/App.tsx`：`rateSelected`、`setFlagSelected` 改单次调用；**撤销路径同样走 bulk**（当前 `App.tsx:488,508` 是逐条 `for`）。
- **契约**：`bulkUpdate(ids: number[], patch: { rating?: number; flag?: number; note?: string; url?: string }): Promise<number>`（返回受影响行数）
- **验收**：选中当前已加载的全部（基准库可造 1,000–2,000 张）改评分 → 只发 1 次 IPC；用 T0-3 基准记录前后耗时；撤销后原值完全恢复。
- **风险**：SQLite 参数上限（32766）→ 已用 400 分组；空数组直接返回 0。

#### T1-2 导入解码合并（M）——替代原 P1

- **改动**：`src/main/importer.ts` 的 `processItem` 与 `makeThumb/analyzeColor/computeDHash`：
  - 一次解码中尺寸（约 1280）到 Buffer；
  - 720 与 260 缩略图由该 Buffer 二次缩放产出（260 可由 720 再缩）；
  - 色彩分析（24×24）与 dHash（9×8）复用同一份小图派生。
- **预期**：像素解码从 4 次降到 1–2 次（RAW 的 Buffer 不再被反复解码）。
- **验收**：同一批 200 张跑基准，耗时下降 ≥30%（以 T0-3 数据判定，未达标则记录原因）；缩略图尺寸/质量抽检无明显劣化；`hash` 与旧值一致（同图对比）。
- **风险**：二次缩放可能轻微改变 dHash → 用 50 张样本比对新旧 hash，差异需在阈值内，否则 dHash 单独从原图算。

#### T1-3 语句与事务（S）——替代原 P5

- **改动**：`importer.ts:747` 的 `db.prepare` 提到循环外；把一批文件的 `UPDATE items` 收进事务（每 50 条提交）；`embeddings.ts:112` 的 INSERT 每 32 条提交一次。
- **验收**：导入 1,000 张（含 100 张重复）耗时对比基线；中断后数据不缺不重。
- **风险**：事务过大导致锁时间变长 → 分批提交。

#### T1-4 进度节流（S）——原 P9

- **改动**：`importer.ts` 的 `report()` 增加 100 ms 节流，末帧与暂停/取消时强制发送。
- **验收**：导入 1,000 张时 IPC 次数下降一个数量级；进度条仍平滑；取消后最终状态一定送达。

#### T1-5 打包瘦身（M）——原 B1

- **改动**：`package.json` 的 `build.files` 增加排除：
  `!**/node_modules/onnxruntime-node/bin/napi-v*/darwin/**`、`!**/.../linux/**`、`!**/.../win32/arm64/**`。
- **验收**：
  1. `release/win-unpacked/.../bin` 只剩 `win32/x64`；
  2. 启动应用后跑一次文本语义搜索，有结果；
  3. 记录安装包与解压体积的前后数值（统一用 MiB 标注）。
- **风险**：原生模块路径被裁错 → 保留配置回滚；不要同时动 `DirectML.dll`（原 B2 需单独验证）。

### 阶段 2：日常手感

#### T2-1 瀑布流（M）——原 P6

- **改动**：`Gallery.tsx` 的 `boxes` 改为增量缓存（只算新增项）；可见区间用列高数组做二分；`onScroll` 用 `requestAnimationFrame` 节流。
- **验收**：5 万项（可用基准数据构造）滚动 ≥ 50 fps；`boxes` 计算次数在追加一页时只增不减。
- **风险**：增量缓存需处理 `thumbSize` / 窗口宽度变化 → 变化时整表失效重建。

#### T2-2 灯箱增强（M）——合并原 F3 + U7

- **改动**：`Lightbox.tsx` 增加缩放（适应 / 1:1 / 滚轮自由）、拖拽平移、全屏、幻灯片播放（3s/5s）。

- **验收**：三档缩放下图片不越界；拖拽后不误关；全屏 Esc 退出；幻灯片在最后一张停住。
- **风险**：与 `App.tsx` 现有 Esc 处理冲突 → 灯箱内部先拦截并 `stopPropagation`。

#### T2-3 图片右键菜单（M）——原 U1

- **改动**：新增 `src/renderer/src/components/ContextMenu.tsx`；`Gallery.tsx` 的 `Card` 与 `Lightbox` 挂 `onContextMenu`。
- **菜单项**：打开、在资源管理器中显示（复用 `showInFolder`）、复制图片、评分、加标签、加入文件夹、堆叠、移除。
- **边界**：只服务图片区；标签/文件夹/智能文件夹的删除留在侧栏右键菜单（D1 已定），不搬进图片菜单。
- **验收**：右键位置不越界（贴边时翻转）；菜单外点击关闭；键盘 Esc 关闭；同一时刻只有一个菜单。

#### T2-4 拖拽失败提示（S）——原 U8

- **改动**：`App.tsx` 的 `handleDropItems` 加 try/catch，失败走 toast；成功保留现有撤销 toast。
- **验收**：拖拽到只读目录/已删除文件夹时给出明确提示，不静默。

### 阶段 5：分发

#### T5-1 发布流程与自动更新（M）

- **托管（D3 已定）**：`build.publish = { provider: 'generic', url: '<存储域名>/moonnest/' }`，对象存储为主通道；GitHub Releases 同步上传一份做备份/手动下载。
- **每次发版必须上传三件**：`月巢 Setup x.y.z.exe`、`latest.yml`、`*.exe.blockmap`（差分更新依赖它）。
- **代码改动**：依赖加 `electron-updater`；`src/main/index.ts` 启动后延迟检查；`SettingsDialog.tsx` 显示当前版本、检查更新、下载进度。
- **失败策略**：检查/下载失败只写日志，不弹错误；用户可手动点"检查更新"。
- **回滚**：把上一版 `latest.yml` 与安装包放回同一目录覆盖，客户端下次检查即回退；保留最近 2 个版本的文件。
- **前置校验**：确认用户是从**安装版**启动（`E:\Apps\image-nest` 那份是 NSIS 装到 E 盘的，注册表有记录，需要实测更新器能否写入原路径），否则会出现"提示有新版但装不上"。
- **验收**：0.1.14 能收到 0.1.15 提示并完成安装；断网时静默失败并落日志；回滚 yml 后能退回旧版。

#### T5-2 代码签名（M，依赖 D4）

- 签名后 `Get-AuthenticodeSignature` 为 `Valid`；SmartScreen 不再提示未知发布者。

#### T5-3 DirectML 裁剪验证（S）——原 B2

- 仅在 `win-unpacked` 手动删除后跑一次推理；成功再落到配置，失败保留文件。

## 五、验收 Gate

| Gate | 通过条件 |
| --- | --- |
| G0 | 日志/崩溃兜底生效；`npm run bench` 可跑出基线 JSON；CSP 无违规 |
| G1 | 1 万张批量操作单次 IPC 且耗时达标；导入耗时较基线下降 ≥30%；打包 bin 只剩 win32/x64 且语义搜索可用 |

### 补充：索引被覆盖安装清掉的修复（0.1.29）

- 事故现象：升级安装后打开应用，图库是空的（原图都在，但索引里一条记录也没有）。
- 根因：0.1.26 允许把索引搬到任意文件夹，用户把索引搬到了**应用安装目录**（`E:\Apps\image-nest\index&cache`，34313 个文件）。覆盖安装会清理安装目录，整个索引被删；`library:last` 找不回索引，用户再点「打开图库」就在图库目录里新建了一个空库，且 `openLibrary` 顺手把失效的映射清掉了，线索全无。
- 修复 1（根因）：`moveIndexTo` 拒绝把索引放进应用安装目录（`dirname(app.getPath('exe'))` 及其子目录），提示"升级安装会把它清掉"。
- 修复 2（不再静默）：`resolveIndexDir` 映射失效时只临时回退，**不再清空映射**（目录找回来就能继续用）。

- 修复 4（能自救）：`syncLibrary` 在没有来源记录、也没有任何图片时按图库根目录兜底扫描，空库点一次「刷新图库」即可重建。
- 实测（CDP）：空库 `syncLibrary` → `scanned 4 / added 3 / total 3`（含子目录递归）；打包版把索引搬进安装目录被拒（提示文案正确）；配置里映射指向不存在的目录 → `lastLibrary` 返回 `indexMissing`、欢迎页出现提示、图库目录里**不会**偷偷建库。

### 补充：灯箱无损缩放（0.1.28）

- 交互：滚轮以光标为锚点缩放（20%~800%，按屏幕物理像素折算）、放大后可拖动平移（超出画布才允许拖，且不越界）、双击在「适应窗口」与「100%」之间切换、`+` / `-` 步进缩放、`0` 回到适应；底栏显示当前比例，并提供缩小 / 放大 / 适应按钮。
- 清晰度：图片仍走 `photo://` 原图（不是缩略图），缩放通过给 `<img>` 设置精确像素宽高实现，浏览器按目标尺寸重新采样；平移只做 `translate3d`，不对已栅格化的位图做 transform 放大，所以放大时不会二次模糊。
- 100% 按 `devicePixelRatio` 折算：系统 175% 缩放时，2000px 宽的原图在 100% 下显示为 1143 CSS px（= 2000 物理像素），像素级检视不会发虚。
- 细节：切换图片自动回到适应；连续滚轮缩放会同步更新内部基准值，避免同一帧内多个 wheel 事件丢步；点击空白仍可退出，拖动后松开不会误关。
- **像素对齐（复查时修掉的真问题）**：原来用 `Math.round(自然宽 × 比例)` 取整 CSS 像素，在 175% 缩放的屏幕上 3000px 宽的图 100% 会变成 2999.5 物理像素，再叠加居中产生的 0.375 物理像素偏移，浏览器会把整张图重采样一遍——放大到"1:1"反而最糊。现在宽度、高度、偏移全部按**整物理像素**取整（`round(px × dpr) / dpr`），并去掉 `will-change: transform`，避免超大图层被合成器按低分辨率栅格化。
- 实测（CDP，3000×3000 的 1px 棋盘图，dpr 1.75，`--disable-gpu` 截图后按物理像素统计）：
  - 修复前 100%：中心 64×64 区域 `pureRatio 0.006`、灰度值 61 种、几乎全是 127 的灰片（整图被重采样）。
  - 修复后 100%：`pureRatio 1.0`、灰度值 2 种、平均梯度 255 —— 纯黑白零插值，真正的 1:1。
  - 381% / 800%：周期 6.7 / 14 物理像素的平滑过渡（双线性放大应有形态），无降采样或整块灰，细节保留。
  - 交互回归同步通过：适应 88%、滚轮 603%、上限 800%、拖动位移不误关、双击 100%、`+` 111%、`0` 回适应、点空白关闭。
- 已知边界：RAW 走导入时抽出的内嵌预览、TIFF/HEIF 预览上限 2560px，超过预览分辨率的部分放大也补不回来（源文件限制，非缩放逻辑问题）。

### 补充：索引可搬离照片目录（0.1.26）

- 背景：图库目录里会自动生成 `library.db` + `-wal` / `-shm` + `thumbnails/` + `previews/`，用户把照片文件夹直接当图库时，这些索引文件会混在照片里。
- 配置：`AppConfig.libraryIndex`（图库路径 → 索引目录的映射，键做小写归一）；没记录就沿用图库目录，老图库零迁移。
- 路径解析：`db.resolveIndexDir()` 决定本次用哪个目录；映射的索引不存在但图库目录里有库文件时自动回退并告警。
- 迁移：`libraryStore.moveIndexTo(target | null)` —— 关库（含 WAL checkpoint）→ 复制文件与缓存 → 写映射 → 重开 → 清理旧位置。复制失败或新位置打不开都会退回原位置；`target = null` 表示搬回图库目录。导入进行中会拒绝操作。
- 连带的路径修正：缩略图/预览（`repo.thumbPathFor / previewPathFor`）、备份快照与缓存打包（`backup.ts`）全部改走 `getIndexPath()`；`library:last` 用解析后的路径判断；新建/恢复图库会清掉同路径的旧映射。
- 界面：设置 → 存储位置（显示图库目录 / 索引目录、`更改位置…`、`放回图库目录`、结果提示）。
- 加固：`openLibrary` 打不开时等 400 ms 重试一次再判定失败（进程刚被强杀、或库文件正被杀毒软件扫描时会出现一次性的 `disk I/O error`）；错误日志带上失败步骤（`open` / `schema` / `migrate`）与释放失败连接，便于定位。
- 实测（CDP，开发与打包产物一致）：
  - 设置面板出现存储位置区块与「更改位置…」按钮，并显示图库路径。
  - 目标目录已有 `library.db` → 拒绝并提示，索引保持原位。
  - 搬到自定义目录：61 个文件、`cleaned=true`，图库仍列出 30 张；原图库目录里 `library.db` / `thumbnails` 均已消失；重新 `openLibrary` 后仍指向新目录。
  - 搬回图库目录：61 个文件、`cleaned=true`，30 张正常，自定义目录里的库文件被清掉。
  - 重启验证：搬到自定义目录后退出重启，仍从新目录加载，30 张正常，`thumb://item/1` 实际加载成功（`naturalWidth > 0`）；正常关窗退出版本 1 次 + 强制结束进程（任务管理器式 `taskkill /F`）版本连续 3 次，均通过。
  - 映射失效：配置里指向一个已被删掉的索引目录，启动后 `indexDir` 回退到图库目录、30 张正常、不会在空目录里新建 `library.db`，且配置里的 `libraryIndex` 被清空。
