# 语义检索性能实测

> 2026-11-04 · 由 `npm run bench:clip` 生成
> 之前只是怀疑「3 万 × 512 维暴力算」是瓶颈，这次把它量出来。

## 一句话结论

**扫描不是最贵的，建缓存才是。** 3 万张时一次检索约 68 ms，其中约 56 ms 是扫描、12 ms 是算筛选 id；
但**首次检索要 875 ms**（读库 + 解码 + 建 Map 缓存），6 万张时到 1.77 s，而且内存是向量本身体积的 2.5 倍。

## 怎么跑

```bash
npm run bench:clip            # 5k / 30k / 60k 三档
npm run bench:clip -- --quick # 只跑 5k / 30k
```

脚本做三件事：
1. 在临时图库里造 N 条随机**归一化**向量（格式与真实索引一致：`embeddings.vec` 存 Float32Array 的字节）；
2. 调用真实的 `searchSimilar(1, 200)`，走完整链路：读向量 → 解码 → `filteredIds` → 逐条点积 → 排序取前 200 → `getItemsByIds`；
3. 输出冷启动、热检索中位数、筛选 id、取详情、RSS 增量与向量本身体积，并落盘到 `.cache/bench/clip-<时间>.json`。

## 环境

- Windows 10.0.26300 x64 · i7-12700KF（20 核）· 31.8 GB
- 模型：Chinese-CLIP，512 维（SigLIP 是 768 维，按同样比例放大）
- 版本 0.2.6

## 结果

| 向量数 | 冷启动 | 热检索（中位） | 其中算筛选 id | 取详情 200 | 内存增量 | 向量体积 |
| --- | --- | --- | --- | --- | --- | --- |
| 5,000 | 48 ms | 5.5 ms | 1.0 ms | <1 ms | +16 MB | 9.8 MB |
| 30,000 | 875 ms | 54.5 ms | 11.8 ms | 1 ms | +147 MB | 58.6 MB |
| 60,000 | 1,772 ms | 116.6 ms | 24.2 ms | 1 ms | +297 MB | 117.2 MB |

热检索 5 次的波动很小（60k：116.0 / 116.3 / 116.6 / 118.1 / 127.7 ms），基本是线性的。

## 拆开看

以 60k 为例：

- 冷启动 1,772 ms − 热检索 117 ms ≈ **1.65 s 花在「把 6 万条 BLOB 读出来、转成 Float32Array、塞进 Map」**，平均每条 27 µs；
- 热检索里扣掉筛选 id（24 ms）和取详情（1 ms），**真正的点积扫描约 91 ms**，平均每条约 1.5 µs；
- 也就是说：**建缓存的单条成本是扫描的 18 倍**。

内存：297 MB 对应 117 MB 的向量本体，约 2.5 倍。原因有两个：
1. 每条向量是一个独立的 `Float32Array`，外加 `Map` 的键值节点；
2. `.all()` 读出来的 BLOB 是临时的 `Buffer`，释放不及时，峰值会把 RSS 一起抬上去。

## 结论（三条）

1. **30k 这个量级，热检索 55 ms 不算灾难**，但它在主进程里同步跑，会卡住 IPC 响应；筛选条件再复杂一点、加上 `filteredIds` 会更久。
2. **首次检索是明显的卡顿点**：启动后或重建索引后的第一次搜索要等 0.9–1.8 s，而且这段时间界面没有任何反馈。
3. **内存换性能的性价比不高**：用了 2.5 倍内存，换来的却是一个每次都要线性扫的缓存；`invalidateClipCache()` 一调用（索引、切库）全部白建。

## 当时的优化建议

| # | 做法 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| 1 | 缓存改成「一块连续 `Float32Array` + 一份 id 数组」，扫描时按 offset 顺序访问 ✅ 已做 | 扫描快 2–4 倍，内存回到接近 1 倍 | 低，纯内部结构 |
| 2 | 缓存增量更新：索引完只追加新向量，不再整个清空 ✅ 已做 | 少一次全量重建 | 中，要处理删除/换模型 |
| 3 | 把首次加载与扫描放进 `utilityProcess` / worker | 主进程不卡，能显示「正在准备语义索引」 | 中，要传向量或共享内存 |
| 4 | 先用筛选结果收窄再算点积 | 只在筛选命中率低时有效（比如只看 1 个文件夹） | 低，但要先拿到有序 id |

当时的估计是「1+2 能把首次压到 100 ms」，**实测证明估错了**：首次慢在读 6 万条 BLOB，不在对象分配。实际结果见下一节。

## 已实施的优化（2026-11-04 晚）

做了上面第 1、2 条：

- 缓存从 `Map<id, Float32Array>` 改成**一块连续的 `Float32Array` + `Int32Array` id 表**，扫描按 `row * dim` 顺序访问；
- 排名从「全量 `sort` 几万个对象」改成**前 K 名小顶堆**，只保留 200 名；
- 读库从 `.all()` 改成 `.iterate()` 逐行，避免几万条 BLOB 同时驻留；
- 索引时按批 `appendClipVectors()` 追加进缓存，不再在结束时整表清空；用 `Set<id>` 去重，防止索引中途检索导致重复；
- 维度对不上的老索引行直接跳过。

### 优化前后

| 向量数 | 冷启动 | 热检索 | 内存增量 | 向量体积 |
| --- | --- | --- | --- | --- |
| 5,000 | 48.4 → **46.7 ms** | 5.5 → **4.7 ms** | 16 → **10.4 MB** | 9.8 MB |
| 30,000 | 874.6 → **834.2 ms** | 54.5 → **46.4 ms** | 147.2 → **63.7 MB** | 58.6 MB |
| 60,000 | 1,771.6 → **1,697.3 ms** | 116.6 → **91.0 ms** | 297.2 → **124.2 MB** | 117.2 MB |

- **内存：降到向量本体的 1.1–1.4 倍**（原来稳定在 2.5 倍），60k 省下 170 MB 左右；具体数字受 GC 时机影响，多次跑会在 63–80 MB（30k）之间浮动；
- **热检索：快 15%–22%**，60k 从 117 ms 降到 91 ms；
- **冷启动只快了 3%–4%**，因为那 1.7 s 根本不是对象分配，而是**从 SQLite 逐行读 6 万条 BLOB**。

### 正确性

基准里加了两项对照，三档全部通过：

- **排名一致**：另写一份「读库 → 逐条点积 → 全量排序」的参照实现，和优化后的堆排名比对前 20 名的 id 与顺序；
- **增量追加**：往缓存里追加三条「几乎等于查询向量」的新向量（不重新读库），必须立刻排到前三；同一批再追加一次，结果里不能出现重复 id。

### 还没解决的

冷启动仍是最大的一块（30k 834 ms / 60k 1.7 s），瓶颈是逐行读 BLOB → 见下一节的快照文件。

上面第 3 条（挪到 worker）也还没做——它解决的是「卡主进程」而不是「慢」，等冷启动降下来之后再评估更划算。

## 向量矩阵快照（已实施）

### 做法

把某个模型的整张向量矩阵落成一个连续文件，启动时一次顺序读进来，不再逐行读 BLOB。

- **位置**：`<索引目录>/vectors/<模型>.bin`，跟着图库走，换库自动隔离；
- **格式**（小端）：`magic 'LUNVEC01'(8) · version(u32) · dim(u32) · count(u32) · maxId(u32)` 共 24 字节头，后面依次是 `ids: Int32Array(count)` 与 `data: Float32Array(count × dim)`；
- **写入**：先写 `.tmp` 再 `rename`，中途崩溃不会留下半个文件；读库建缓存后、以及索引结束时各写一次；
- **读取**：校验 magic / version / dim / **条数 / 最大 id**（与库里的 `COUNT(*)`、`MAX(item_id)` 比），任一不符就退回读库并重写快照；
- **零拷贝**：`readFile` 的 Buffer 对齐时直接用 `new Float32Array(buffer.buffer, offset, len)` 做视图，不再复制一遍。

### 效果（同一次运行内对比）

| 向量数 | 冷启动（读库） | 冷启动（快照） | 加速 | 热检索 | 内存增量 |
| --- | --- | --- | --- | --- | --- |
| 5,000 | 50.3 ms | **28.2 ms** | 1.8× | 5.0 ms | 20.2 MB |
| 30,000 | 365.0 ms | **77.8 ms** | 4.7× | 22.5 ms | 64.0 MB |
| 60,000 | 734.5 ms | **138.6 ms** | 5.3× | 43.9 ms | 124.8 MB |

30k 首次检索从 365 ms 降到 78 ms，回到「眨眼之间」的量级。

> 注意：同一台机器不同时段跑，读库那一路的绝对值能差到 2 倍（白天测是 830 ms，深夜稳定在 365 ms），
> 所以只有**同一次运行内**的「读库 vs 快照」才有可比性；上面的加速比就是这么算的。

### 正确性

除了「排名一致」「增量追加」，又加了一项 **快照失效**：

- 删掉一条向量 → 清缓存 → 再检索，必须自动回退读库、删掉的那条不再出现，且前 20 名与参照实现一致。

三档全部通过（`排名一致 / 增量追加 / 快照失效 = 是`）。

### 仍然存在的

- **索引刚跑完、还没检索过**：此时缓存是空的，第一次检索仍要读一次库（30k 约 365 ms）然后才写快照；
  想连这一次也省掉，得在索引结束时直接按库生成快照，代价是多一次 365 ms 的后台读。
- **主进程同步扫描**：热检索 22 ms（30k）/ 44 ms（60k）仍在主线程上跑，量大时会有轻微卡顿；要彻底解决还是得挪 worker。

## 这次没测到的

- 文本塔推理时间：`searchByText` 还要跑一次 ONNX 文本编码，本机没下模型，没算进去；真实使用会比这里的数字再多一次模型推理。
- 磁盘与冷 OS 缓存：临时库刚写完就在页缓存里，实际冷启动可能更慢。
- 768 维模型：按比例推算 60k 约 175 MB 体积、热检索 ~88 ms。
